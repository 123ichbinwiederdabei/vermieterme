**Krandorf 7 billing audit — 8 October 2026**

The app is not ready to issue a settlement that meets the supplied requirements for billing from 1 October 2026. Several current paths omit costs, use the wrong allocation key, or return an apparently complete statement from incomplete data.

Audited source: commit `527b9f3d985145d97d673130bfa2ca046df71451` on `recover/live-image14`. The source was previously recovered from the retained image-14 build. Production uses `img-captain-vermieterme:14`, image ID `sha256:11f62c3ce8065add0f76aa7bd032e3e6e9d134a5cbce8483296ea29d5fcb525e`.

The audit covered billing domain functions, input/write APIs, snapshot application, landlord UI calculations, PDF/tenant statement paths, and the relevant production configuration. Production SQLite was opened read-only. No application source, production records, or services were changed. This is a billing correctness and requirements audit; it does not certify the facts needed for a statutory exception or perform a separate security audit.

**Confirmed findings**

P1 means a material billing error or a missing guard needed before issuing bills. P2 means an additional correctness or auditability defect. Runtime examples below use synthetic fixtures, not actual customer invoices.

1. **P1 — Manually entered costs do not reach the final calculation.** The cost editor saves `totalAmount`/`unitAmount` as JavaScript numbers. Its API never writes `totalAmountCents` or `CostAllocation`. The manual preview reads only `totalAmountCents`, defaulting null to zero. The statement builder reads only allocations and has no completeness check. The UI exposes preview/apply for Grundsteuer and Kleinkläranlage, but not ordinary manual categories such as Müll or water. A synthetic €390 water entry therefore becomes €0 in the cent-based preview. A statement with an entered charge but no allocations can return €0 actual costs and a €1,200 refund from prepayments. This affects landlord PDF and tenant output because both use the same statement builder. The required repair is one server-side cost-to-allocation pipeline and a completeness gate before final issuance, including explicit zero-cost confirmation where appropriate. Evidence: [cost write API](../../src/app/api/billing-periods/[id]/costs/route.ts), [manual preview](../../src/lib/manual-cost-preview.ts), [statement builder](../../src/lib/billing-statement.ts), and [billing UI](../../src/app/billing/[id]/page.tsx). Key lines: API 82–104; preview 69; statement 28–62; UI 580.

2. **P1 — Heating is always area-based, including a bypassed standard mode.** `buildHeatingOilPreview` never uses `consumptionSharePercent`, `baseSharePercent`, or individual heat readings when allocating costs. It uses only connected-unit area. The standard-mode guard checks whether `consumptionSource` equals the string `NONE`; setting another string passes that guard without introducing any measured heat-consumption calculation. A runtime fixture in standard mode with a declared heat source returned no blockers and still used area. OilFox measures tank fuel consumption, which does not establish each tenant's heat consumption. Standard allocation ordinarily requires 50–70% based on measured heat use; keep that mode blocked until its calculation and data validation exist. Evidence: [heating preview](../../src/lib/energy-preview.ts), lines 115 and 180–194. Legal reference: [§7 HeizkostenV](https://www.gesetze-im-internet.de/heizkostenv/__7.html).

3. **P1 — Section 11 evidence is not structured or validated.** Creation/update requires a nonempty exception reason, and preview checks only that reason. It does not validate the reason code, applicability, effective dates, or supporting evidence. Live configuration has a generic technical-impossibility/high-cost reason, with no code, validity dates, or document reference. The runtime fixture with only free text returned no blockers. This violates AGENTS.md even before deciding whether the exception is legally available. Section 2 is also not established by the present records: three units are recorded and no contractual evidence is linked. Establish the building configuration and exception facts before choosing a mode; do not infer an exception from missing meters. Evidence: [heating API](../../src/app/api/heating-oil/route.ts), lines 51–57 and 79–102; [preview](../../src/lib/energy-preview.ts), lines 118–120. Legal references: [§11 HeizkostenV](https://www.gesetze-im-internet.de/heizkostenv/__11.html) and [§2 HeizkostenV](https://www.gesetze-im-internet.de/heizkostenv/__2.html).

4. **P1 — Required CO₂ input is silently replaced by zero.** The opening-stock and delivery forms initialize CO₂ cost/emissions to zero and expose no corresponding input controls. The API accepts those defaults, and preview has no missing-evidence blocker. All five live inventory lots currently carry zero CO₂ cost and emissions, so the calculated landlord deduction is zero. A zero value needs evidence where legitimate; it must not stand for unknown invoice data. The PDF prints aggregate emissions and the landlord deduction but omits the tenant CO₂ share, tier, and calculation basis. Evidence: [heating form](../../src/app/heating-oil/page.tsx), lines 37–38 and 135–136; [heating API](../../src/app/api/heating-oil/route.ts), lines 147–150 and 167–170; [PDF](../../src/lib/billing-v2-pdf.tsx). Disclosure reference: [§7 CO2KostAufG](https://www.gesetze-im-internet.de/co2kostaufg/__7.html).

5. **P1 — CO₂ tier classification truncates instead of rounding.** Integer division floors the specific emissions to one decimal before thresholds are applied. At 3,346,000 g over 280 m² for a 365-day year, the intensity is 11.95 kg/m²/year. The app returns 100% tenant share; rounding to 12.0 requires the 90% tenant/10% landlord tier. This can omit a material landlord deduction near every tier boundary. Use exact integer rounding before classifying, with explicit short-period handling. Evidence: [CO₂ function](../../src/lib/energy-billing.ts), lines 43–56. Legal references: [§5 CO2KostAufG](https://www.gesetze-im-internet.de/co2kostaufg/__5.html) and [its tier table](https://www.gesetze-im-internet.de/co2kostaufg/anlage.html).

6. **P1 — Kleinkläranlage uses the wrong key.** The preview unconditionally builds weights from area and labels allocations `AREA`, ignoring the required thirds. A €390 eligible bill produces €80 Isabella, €200 Vladimir, and €110 owner, instead of €130 each. Changing a category label/key in settings does not fix the hard-coded allocation. Use an explicit category-specific agreement with the owner as a participant. Evidence: [wastewater preview](../../src/lib/cost-invoice-billing.ts), lines 103–124.

7. **P1 — Grundsteuer includes the owner's area.** Both rate calculation and allocation iterate all property units. For an already isolated €280 rental residential component, the amount method charges Isabella €57.44 and Vladimir €143.59, leaving €78.97 with the owner; the requested rental-only allocation is €80/€200. Rate mode calculates a 390 m² component instead of 280 m². There is also no validation that the allocatable amount/rate-derived amount does not exceed the stated assessment. Add explicit tax-eligible rental areas/components, an evidenced residential tax basis, and a conservation check. Excluding land/garden/garage components is a supplied project requirement, not a conclusion that the entire statutory tax is inherently nonrecoverable. Evidence: [manual preview](../../src/lib/manual-cost-preview.ts), lines 73–105 and 118–122; [setting API](../../src/app/api/properties/[id]/property-tax-setting/route.ts), lines 22–29.

8. **P1 — Intermediate electricity readings do not determine the tenant's charge.** The electricity preview demands readings at tenant-change boundaries, then adds all interval costs to a unit total. It subsequently splits that total across tenants by occupied days. A fixture with equal five-day occupancies and measured consumption costing €900 before the change and €100 after it charges €500 each. Preserve the tenant identity on each consumption interval; prorate fixed/common charges separately under the agreed key. The shared generic tenant-split function also provides only time-based splitting for heating allocations and contains no documented consumption-based fallback. Evidence: [electricity preview](../../src/lib/energy-preview.ts), lines 259–295 and 318–327; [tenant split](../../src/lib/energy-billing.ts), lines 70–94. Heating changeover reference: [§9b HeizkostenV in the official text](https://www.gesetze-im-internet.de/heizkostenv/HeizkostenV.pdf).

9. **P1 — Snapshot scope and issued-statement reproducibility are unsafe.** Apply supersedes by period and `kind`, omitting the category ID. Applying a tax `MANUAL` snapshot superseded an unrelated water `MANUAL` snapshot in the runtime reproduction. Apply also deletes previous category allocations, toggles existing lot-consumption rows, and stores only a fingerprint in `sourceJson`. The statement uses current allocation rows, active financial periods, and current tenant/unit metadata rather than a frozen statement revision; it does not reject stale snapshots. Consequently an old PDF is not a stable view of an issued revision. Scope supersession to the correct category/revision and preserve immutable allocation, consumption, prepayment, input, and statement versions, with an explicit final-issuance guard. Evidence: [apply API](../../src/app/api/billing-periods/[id]/energy-preview/route.ts), lines 29–67; [statement builder](../../src/lib/billing-statement.ts), lines 32–36 and 49–77. The broad snapshot update is runtime-confirmed; the other persistence/reconstruction issues are traced statically.

10. **P1 — The full heating cost pool is not implemented.** Heating preview totals only FIFO oil-lot cost. It does not load/add maintenance, service, chimney/emission inspection invoices, or heating-plant electricity. Supported electricity roles include the wastewater plant but no distinct heating-plant role. Labeling heating electricity as household/common electricity would charge it through the electricity pool instead of the heating pool. Build one eligible heating operating-cost pool, with protection against duplicate chimney or electricity charges, then apply the validated heating allocation. Evidence: [heating preview](../../src/lib/energy-preview.ts), lines 126–172; [meter roles](../../src/app/api/electricity/route.ts), lines 85–89. Eligible heating operating costs are described in [§7(2) HeizkostenV](https://www.gesetze-im-internet.de/heizkostenv/__7.html) and [§2 BetrKV](https://www.gesetze-im-internet.de/betrkv/__2.html).

11. **P2 — Electricity loses precision at every interval.** The helper rounds each interval to cents before the preview sums them. Two 1 kWh intervals at €0.0049/kWh each produce zero cents, although their combined price rounds to one cent. Extra intermediate readings can therefore change a bill without changing total consumption. Retain integer micro-euro quantity products until final deterministic cent allocation. Evidence: [electricity pricing](../../src/lib/billing-v2.ts), lines 128–141; [interval accumulation](../../src/lib/energy-preview.ts), lines 285–295. Runtime-confirmed.

12. **P2 — A consumption-weighted Grundpreis disappears at zero consumption.** With all readings unchanged, every base-price weight is zero. `allocateCents` returns zeros, and total billing is reconstructed from allocations rather than the payable contract base price. The reproduction has a €100 monthly base price, zero consumption, and a returned total of €0. Require a documented zero-consumption fallback or a blocker rather than silently dropping the charge. Evidence: [base-price allocation](../../src/lib/energy-preview.ts), lines 302–310 and 331–343; [allocation helper](../../src/lib/billing-v2.ts), line 36. Runtime-confirmed.

13. **P2 — Contract and meter validity do not constrain consumption.** The preview uses tariff dates but does not intersect consumption ranges with contract/meter `validFrom`/`validTo`. An inactive future meter with otherwise available readings was charged for the current period in the reproduction. Tariff billing-date overrides are also checked incompletely for overlap or undocumented deviation. Include effective contract/meter ranges and validate settlement intervals independently of the original tariff intervals. Evidence: [electricity preview](../../src/lib/energy-preview.ts), lines 240–277; [tariff API](../../src/app/api/electricity/route.ts), lines 43–58 and 65–75. Future-meter charging is runtime-confirmed; the remaining validation gaps are static.

14. **P2 — Plant electricity is missing from wastewater provenance/invalidation.** The wastewater result includes metered plant electricity, but its source fingerprint hashes only invoices and unit areas. Doubling a tariff changed the preview amount while leaving its fingerprint unchanged. Tariff updates mark `ELECTRICITY` snapshots stale, not `SMALL_WASTEWATER`; reading/invoice changes also lack complete dependency invalidation. Hash and retain all electricity/tenancy/agreement inputs and invalidate every dependent cost category. Evidence: [wastewater fingerprint](../../src/lib/cost-invoice-billing.ts), line 127; [tariff update](../../src/app/api/electricity/route.ts), line 75; [invoice mutation API](../../src/app/api/cost-invoices/[id]/route.ts). Fingerprint omission is runtime-confirmed.

15. **P2 — Wastewater electricity can be charged twice, and excluded costs break the total invariant.** `BETRIEBSSTROM` invoice lines are eligible, and metered plant electricity is always added on top; no source distinction prevents entering the same electricity invoice and charging its measured consumption again. Separately, `totalAmountCents` contains only eligible charges, while `landlordAmountCents` adds excluded repairs as well as vacancy. An eligible €100 plus excluded €50 can therefore report a €100 total and combined tenant/landlord amounts of €150. Separate total invoice cost, recoverable cost, owner operating share, and excluded owner-only cost; require each electricity source once. Evidence: [wastewater preview](../../src/lib/cost-invoice-billing.ts), lines 93–102 and 128; [eligible classifications](../../src/lib/cost-invoice.ts), lines 3–6. Static trace; the repair-classification exclusion itself passed the isolated check.

16. **P2 — Tenant billing lists include superseded and nonoverlapping periods.** The list loads every property period without a status or tenancy-overlap filter and invokes the statement builder through `Promise.all`. A period outside a tenant's occupancy throws and causes the entire list to fail. Superseded periods can appear alongside their replacements. Filter eligible periods first and expose only the intended statement revisions. Evidence: [tenant billing list](../../src/app/api/tenant-app/billing-periods/route.ts), lines 11–12; [statement overlap guard](../../src/lib/billing-statement.ts), lines 37–39. Static trace.

The landlord UI independently computes shares and advances with floats, recognizes automatic distribution only for `MEA`, and otherwise uses one manually entered unit amount. It does not consume the exact per-tenant domain statement used by the PDF. This is an additional manifestation of finding 1 and violates the shared-server calculation rule. See [billing UI](../../src/app/billing/[id]/page.tsx), lines 374–397, and [legacy totals](../../src/lib/billing.ts), lines 65–101. Owner-occupied shares are also labeled as vacancy by the generic splitter, although retaining the money with the owner is numerically correct for the water fixture.

**Verification and limits**

Fifteen isolated requirements checks ran under Node 22, with mocked Prisma responses and synthetic billing inputs, against the real domain/API functions. Thirteen failed and two passed. Passing checks confirmed the 390 m² water split when a valid cent value reaches the domain and the exclusion of repair/replacement/refurbishment/modernization classifications. The failures are requirements regression reproductions; they are not environmental startup failures. Machine-readable results are in [the evidence file](2026-10-08-krandorf7-evidence.json). Reproduction fixtures and instructions are retained in [krandorf7-checks](krandorf7-checks/README.md); the original test log is also retained at `/tmp/vermieterme-krandorf-audit`.

The previously completed 86 unit/API tests and five browser tests did not cover these allocation/evidence edge cases. This audit did not rerun a production deployment or modify the existing suite. Static-only findings are labeled above. The actual leases, supplier invoices, exception documents, tax calculation, and complete building topology were not supplied or reviewed; their substantive eligibility cannot be inferred from the database text. No actual settlement total is asserted by the synthetic examples.
